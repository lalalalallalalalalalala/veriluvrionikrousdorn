# Формат `.vlr` (черновик)

Родной исполняемый формат Veriluvrionikrousdorn. Версия формата в этой вехе — **0**.
Это значит, что раскладка ещё может измениться. Загрузчик умеет проверить магию
и прочитать фиксированный заголовок (`vlr_loader::parse_header`) и на этом
останавливается: отображать секции и переходить в код он не умеет.

Первым исполняемым файлом этого формата будет оболочка **vch**. Сейчас она
встроена в ядро. Позже тот же интерфейс переедет в `/Apps/vch/vch.vlr`.

## Файл

- Расширение: `.vlr`
- Разрядность: только 64-bit
- Порядок байт: little-endian
- Магия, 4 байта: `7F 56 4C 52` (`\x7FVLR`, по аналогии с `\x7FELF`)

## Фиксированный заголовок (32 байта)

| Смещение | Размер | Поле | Значение |
| --- | --- | --- | --- |
| 0 | 4 | magic | `7F 56 4C 52` |
| 4 | 2 | format_version | `0` в этом черновике |
| 6 | 2 | kind | `1` исполняемый файл, `2` общая библиотека |
| 8 | 2 | flags | пока `0`; младший бит зарезервирован под позиционно-независимый образ |
| 10 | 2 | header_size | размер фиксированного заголовка, сейчас `32` |
| 12 | 2 | section_count | число секций следом |
| 14 | 2 | import_count | число записей импорта |
| 16 | 8 | entry_rva | точка входа, смещение от `image_base` |
| 24 | 8 | image_base | предпочтительный виртуальный адрес образа |

Дальше, по смещению `header_size`, идёт таблица секций, затем таблица импорта.
Их разбор — часть будущего загрузчика; размеры ниже нужны, чтобы не выбирать
их заново.

### Секция (56 байт, черновик)

| Поле | Размер | Смысл |
| --- | --- | --- |
| name | 16 | короткое имя, дополненное нулями (`.text`, `.data`, `.rodata`) |
| file_offset | 8 | смещение в файле |
| file_size | 8 | сколько байт читать из файла |
| virt_addr | 8 | виртуальный адрес |
| virt_size | 8 | размер в памяти; хвост добивается нулями |
| flags | 4 | бит 0 — чтение, бит 1 — запись, бит 2 — исполнение |
| pad | 4 | нули, чтобы структура была выровнена |

### Импорт (64 байта, черновик)

| Поле | Размер | Смысл |
| --- | --- | --- |
| library | 32 | имя файла библиотеки, не путь: `libdraw.vlr` |
| symbol | 32 | имя символа |

Путь к библиотеке выбирает загрузчик, а не файл. Так один и тот же `.vlr`
работает, куда бы ни положили `/Libs`.

## Как это стыкуется с каталогами

Подробности иерархии — в [layout.md](layout.md). Для `vch`:

- программа и исполняемый файл: `/Apps/vch/vch.vlr`
- данные (настройки, пользовательские файлы, кэш): `/AppData/vch/`
- общие библиотеки: `/Libs/`
- частная библиотека, если она есть только у vch: `/Apps/vch/<файл>`
- дом пользователя в приглашении: `~`, сейчас это `/Users/user`

Имя пользователя в заголовок не входит. Его даёт сессия. Пока учёток нет,
ядро подставляет `user`, и приглашение выглядит так:

```text
user@::vch#~ help
```

`~` — текущий каталог, когда он совпадает с домом. Формат строки фиксирован:
`{пользователь}@::vch#{каталог} `, затем набранная команда.

Поиск библиотек из таблицы импорта:

1. `/Apps/<приложение>/<library>`
2. `/Libs/<library>`

Корень данных процесса загрузчик сообщает приложению как `/AppData/<приложение>/`.
Читать эти каталоги можно будет после Btrfs только для чтения. Создавать
`/AppData` при первом запуске — после поддержки записи.

## Чего загрузчик ещё не делает

- не отображает секции в адресное пространство;
- не выполняет релокации и не связывает импорт;
- не переключает кольцо защиты и не прыгает на `entry_rva`;
- не открывает файл с диска: блочного драйвера и Btrfs ещё нет.

`vlr_loader::load` возвращает ошибку «не реализовано» даже для корректной магии.
Это сделано специально, чтобы вызов не притворялся успешным запуском.
